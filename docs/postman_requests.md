# Elevate Online Exams — API Overview

Source: Postman collection **"Elevate Online Exams"** (imported directly into Postman and read endpoint-by-endpoint; not guessed from the documenter page). This is documentation only — nothing here is wired into the Flutter project yet (no Retrofit clients, no repositories, no models).

## Base URL

```
https://exam.elevateegy.com/api/v1
```

Every path below is relative to this base URL.

## Authentication mechanism

Custom raw header, **not** the standard `Authorization: Bearer <token>` scheme:

```
token: <JWT>
```

The JWT is returned by `POST /auth/signin` (and presumably `signup`) and must be attached as the `token` header on every subsequent request. Confirmed by inspecting the collection's saved example headers on 21 of the 25 requests (every endpoint except `signup`, `signin`, `forgotPassword`, `verifyResetCode`, `resetPassword`, which are public).

**Confirmed error envelope** (captured from live 401 responses while testing with the collection's saved example credentials/token, which are stale):

```json
{
  "message": "incorrect email or password",
  "code": 401
}
```

```json
{
  "message": "user not found",
  "code": 401
}
```

So every endpoint that requires auth returns `{ message: string, code: number }` on failure. This shape is used consistently below.

**Success response bodies below are marked "confirmed" only where a live call actually returned one.** The example credentials/token saved in the collection no longer work against the live backend (every authenticated call returns the 401 above), so most success shapes are the request's own saved example body reflected back, or reasonably inferred from field names — never fabricated from nothing. Re-verify against a real successful response once a valid test account exists.

## Standard headers (all requests)

Auto-generated by the HTTP client (Content-Type: application/json, Accept, etc.) — nothing custom beyond the `token` header noted above. Endpoints with a file upload use `multipart/form-data` instead of `application/json` (called out explicitly where it applies).

## Module structure

```
Authentication (10)
├── Sign Up               POST   /auth/signup
├── Sign In                POST   /auth/signin
├── Change Password        PATCH  /auth/changePassword
├── Delete My Account      DELETE /auth/deleteMe
├── Edit Profile           PUT    /auth/editProfile
├── Logout                 GET    /auth/logout
├── Get Logged User Info   GET    /auth/profileData
├── Forgot Password        POST   /auth/forgotPassword
├── Verify Reset Code      POST   /auth/verifyResetCode
└── Reset Password         PUT    /auth/resetPassword

Exams (4)
├── Add Exam                     POST /exams               (admin)
├── Get All Exams                GET  /exams
├── Get All Exams on Subject     GET  /exams?subject={id}
└── Get Exam By Id               GET  /exams/{id}

Questions (6)
├── Add Question                 POST /questions            (admin)
├── Get All Questions            GET  /questions
├── Get All Questions on Exam    GET  /questions?exam={id}
├── Get User History             GET  /questions/history
├── Get Single Question          GET  /questions/{id}
└── Check Questions (submit)     POST /questions/check

Subjects (5)
├── Add Subject                  POST   /subjects           (admin, multipart)
├── Update Subject                PUT    /subjects/{id}      (admin, multipart)
├── Delete Subject                DELETE /subjects/{id}      (admin)
├── Get All Subjects              GET    /subjects
└── Get Single Subject            GET    /subjects/{id}
```

Note on the brief's assumed shape (`Login`/`Register`, `Start Exam`/`Submit Exam`, `Answer Question`): the real collection names things differently and there is no separate "start exam" call — a client fetches the exam via `Get Exam By Id`, fetches its questions via `Get All Questions on Exam`, then submits everything at once via `Check Questions` (`POST /questions/check`), which is the actual submit/grade step. Mapped explicitly in each section below.

## Authentication

### Sign Up (Register)
`POST /auth/signup` — public, no `token` header.

Request body (`application/json`):
```json
{
  "username": "elevate11233",
  "firstName": "Elevate",
  "lastName": "Tech",
  "email": "admin133@1elevate.com",
  "password": "Elevate@123",
  "rePassword": "Elevate@123",
  "phone": "01094155711"
}
```
Response: not confirmed live (no valid test path that doesn't create real data was attempted, per the "no side effects" constraint on this documentation pass). Expect a `201`/`200` with a `message` and likely `user`/`token` — verify once implementing.

### Sign In (Login)
`POST /auth/signin` — public, no `token` header.

Request body:
```json
{
  "email": "admin133@1elevate.com",
  "password": "Elevate@123"
}
```
Response — **confirmed live** (401, invalid saved credentials):
```json
{ "message": "incorrect email or password", "code": 401 }
```
Success shape not confirmed live. Given the auth header pattern (`token`) and that `Get Logged User Info` exists as a separate call, expect something like `{ message, token, user: {...} }` — verify once a real account is available.

### Change Password
`PATCH /auth/changePassword` — requires `token` header.

Request body:
```json
{
  "oldPassword": "Bl77@2222",
  "password": "Elevate@123",
  "rePassword": "Elevate@123"
}
```

### Delete My Account
`DELETE /auth/deleteMe` — requires `token` header. No request body.

### Edit Profile
`PUT /auth/editProfile` — requires `token` header.

Request body (partial update — collection's example only sends one field, so this endpoint likely accepts any subset of the profile fields):

### Logout
`GET /auth/logout` — requires `token` header. No request body.

## Questions

### Add Question *(admin)*
`POST /questions` — requires `token` header.

Request body:
```json
{
  "question": "How can you open a link in a new tab/browser window?",
  "A1": "<a href='url' new>",
  "A2": "<a href='url' target='new'>",
  "A3": "<a href='url' target='_blank'>",
  "A4": "~",
  "correct": "A3",
  "subject": "670037f6728c92b7fdf434fc",
  "exam": "670070a830a3c3c1944a9c63"
}
```
Fixed 4-option MCQ shape: `A1`–`A4` are the choices, `correct` holds which key (`"A1"`–`"A4"`) is right. `subject` and `exam` are ids.

### Get All Questions
`GET /questions` — requires `token` header.

### Get All Questions on Exam
`GET /questions?exam={examId}` — requires `token` header.

Query params:
| Key | Example value |
|---|---|
| `exam` | `670070a830a3c3c1944a9c63` |

This is the call a client makes to fetch the question set for a specific exam session — the closest equivalent to "start exam" (no separate session-start endpoint exists).

### Get User History
`GET /questions/history` — requires `token` header.

Likely returns the logged-in user's past exam attempts/answers. Response shape not confirmed live.

### Get Single Question
`GET /questions/{questionId}` — requires `token` header.

Example: `GET /questions/6715e98c76fb224b2ffe2c`

### Check Questions (submit exam answers)
`POST /questions/check` — requires `token` header.

This is the real "submit exam" action — grades a batch of answers.

Request body:
```json
{
  "answers": [
    { "questionId": "6715e98c76fb2b224b2ffe2c", "correct": "A4" },
    { "questionId": "6715e98d76fb2b224b2ffe2f", "correct": "A4" }
  ],
  "time": 10
}
```
`answers` is an array of `{ questionId, correct }` pairs — one per question the user answered (`correct` here is the user's *chosen* answer key, reusing the same `A1`–`A4` vocabulary as the question, not necessarily the actual correct one — the server presumably compares it against the stored `correct` value per question). `time` is a number (unit not confirmed — likely minutes or seconds spent). Response not confirmed live; expect a score/result summary.

## Open items for Phase 2 (Auth module) and beyond

- Every endpoint (aside from the 5 public auth ones) returned `401 { message: "user not found"/"incorrect email or password", code: 401 }` when tested — the collection's saved credentials/token are stale. A fresh `signup` + `signin` should be run once implementation starts to capture real success response shapes (user object fields, token format, exam/question/subject list envelopes — possibly paginated like the reference project's `results`/`metadata`/`data` pattern, not confirmed either way here).
- `duration` (Exams) and `time` (Check Questions) units aren't confirmed (minutes vs. seconds).
- `Edit Profile`'s accepted field set beyond `lastName` isn't confirmed (presumably any of `firstName`, `lastName`, `username`, `email`, `phone`).
- Subject icon upload is multipart — the network layer skeleton (Phase 1) uses a plain `Dio()` with JSON-oriented interceptors; multipart requests will need `FormData` handling when the Subjects feature is built.
